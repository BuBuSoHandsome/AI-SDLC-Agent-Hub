# Function Point 拆分指引

## 目标

将银行业务需求拆分为业务粒度的 Function Point。Function Point 必须代表一项可独立理解、设计、估算、开发、测试和验收的业务能力。

以业务目标和核心业务动作识别功能点边界，并按客户旅程或产品业务生命周期组织功能点。结合业务对象、状态变化、角色责任、资金或账务影响、风险及合规控制判断功能点是否需要拆分或合并。

银行业务视角用于识别需求中明确涉及的功能点，并在拆分完成后检查遗漏；不得脱离需求原文，将银行通常具备但原文未明确涉及的能力直接补充为已确认功能点。

## 核心判定标准

一个 Function Point 应同时满足以下条件：

1. 有明确的业务参与者或责任角色。
2. 有明确的业务目标。
3. 包含一个完整的核心业务动作。
4. 产生可识别的业务结果，例如业务记录、状态变化、审批结果、资金或账务结果、业务凭证等。
5. 能够追溯到支持它的需求原文。
6. 粒度足以支持独立理解、设计、估算、开发、测试和验收。

功能点应使用“动词＋业务对象”命名，例如“创建贷款申请”“审批支付交易”“执行账户扣款”。

不得仅因某项内容出现在不同页面、渠道、角色或业务视角中，就重复建立功能点。同一业务能力只保留一个 Function Point，并完整描述其适用范围。

## 拆分流程

### 1. 识别业务主线

根据需求内容，选择客户旅程或产品业务生命周期作为功能点的主要组织顺序，例如：

- 客户旅程：了解、申请、开通、使用、变更、查询、终止。
- 产品生命周期：产品定义、申请、审批、签约、生效、存续管理、变更、到期、结清或销户。

不得为了套用上述阶段而补充原文未描述的业务环节。

### 2. 识别候选功能点

在各业务阶段中，识别具有独立业务目标和业务结果的核心业务动作，形成候选 Function Point。

优先使用“谁，在什么业务场景下，执行什么动作，遵循什么规则，产生什么业务结果”理解功能点边界。

### 3. 使用银行业务视角识别与补全

从下述视角检查需求原文，补充原文明确涉及但尚未识别的候选功能点，并检查已有功能点的边界和描述是否完整。

这些视角是分析工具，不是额外的功能点分类，也不是要求每个功能点逐项填写的字段。

### 4. 合并与拆分

按照本指引的拆分规则，合并同一业务动作下的页面、字段、接口、校验和异常步骤；仅将满足独立业务能力条件的内容拆分为单独功能点。

### 5. 检查原文依据

为每个功能点记录原文出处。原文不能明确支持的功能或业务规则，不得写成已确认内容；需要进一步确认的，记录为 Open Item。

### 6. 执行提交前检查

检查功能点的完整性、独立性、粒度、一致性和可追溯性，再提交 Function Point 概览供用户确认。

## 银行业务识别与补全视角

### 1. 客户与客户旅程

检查需求是否明确涉及：

- 不同客户类型、客户分层或客户准入条件。
- 客户从申请、开通、使用、变更到退出的业务动作。
- 客户在业务办理前后的查询、补充材料、确认和结果获取。
- 不同客户在资格、额度、价格、材料或流程上的差异。

不得仅因客户类型不同就重复拆分相同业务能力；只有业务目标、规则或处理流程形成独立业务能力时才拆分。

### 2. 产品与业务全生命周期

检查需求是否明确涉及：

- 产品定义和业务参数维护。
- 业务申请、审批、签约和生效。
- 存续期使用、变更、计息、收费或额度管理。
- 冻结、挂失、展期、提前终止等存续期动作。
- 到期、结清、销户及后续管理。

以生命周期组织功能点，不代表每个生命周期阶段都必须存在功能点。

### 3. 银行内部岗位与运营作业

检查需求是否明确涉及：

- 客户经理、柜员、运营、审批、风险、合规、财务、客服或业务管理员等角色。
- 接件、处理、复核、授权、退回、交接和人工异常处理。
- 总行、分行、支行或其他组织层级的业务职责。
- 业务参数维护、运营查询和内部管理。

当内部角色具有独立的业务目标、处理状态或运营流程时，应拆分为独立功能点；如果只是同一业务动作内部的系统校验、自动处理或职责步骤，不单独拆分。

### 4. 渠道与服务触点

检查需求是否明确涉及：

- 不同渠道的办理、查询、变更或撤销能力。
- 渠道特定的准入、认证、授权或业务规则。
- 跨渠道接续办理、结果查询和状态一致性。
- 客户渠道与银行内部渠道之间的业务衔接。

同一业务能力在多个渠道提供时，默认保留为一个功能点，并在描述中说明渠道差异；只有渠道形成独立业务目标或独立运营流程时才单独拆分。

### 5. 交易状态与异常处理

检查需求是否明确涉及：

- 业务状态及状态变化。
- 撤销、冲正、退款、退货或终止。
- 超时、重复提交、部分成功和处理结果未知。
- 重试、补单、人工介入和状态修复。
- 日终、批处理及对账差异处理。

普通拒绝、校验失败、超时、重试和取消，默认作为主功能的异常分支。只有异常处理具有独立业务目标、独立角色、独立状态、独立资金或账务影响，或者独立运营流程时，才拆分为独立功能点。

### 6. 风险、合规与安全控制

检查需求是否明确涉及：

- 客户身份识别和业务准入。
- 反洗钱、反欺诈、名单筛查或客户适当性。
- 限额、授权、复核和职责分离。
- 身份认证及交易安全控制。
- 客户信息保护、数据授权和隐私要求。
- 操作留痕和审计追踪。

作为同一业务动作内部控制步骤的校验，不单独拆分；具有独立业务目标、角色、状态或处理流程的风险及合规能力，可以独立拆分。

### 7. 资金、账务、清算与对账

检查需求是否明确涉及：

- 扣款、入账、转账和资金冻结。
- 本金、利息、手续费、优惠或税费处理。
- 会计处理、清算和结算。
- 客户账、银行账或其他相关账目之间的一致性。
- 对账、差错处理、调账和凭证生成。
- 交易日、记账日、起息日或到账日等业务时间差异。

资金或账务处理是否独立拆分，应根据其是否具有独立业务目标、业务结果或运营流程判断，不得仅因存在单独接口或会计步骤就拆分。

### 8. 数据、经营分析与监管要求

检查需求是否明确涉及：

- 业务数据的形成、维护和归档。
- 经营分析、业务统计和管理查询。
- 监管报表、监管报送和统计口径。
- 数据查询、导出和留存。
- 合同、凭证和业务影像资料管理。

不得将单个字段、查询条件或报表列拆分为功能点；只有完整的数据管理、统计、报送或归档业务能力才可作为功能点。

## 拆分规则

1. **按业务能力拆分。** 使用“动词＋业务对象”命名，确保功能点具有明确的业务动作和业务结果。

2. **保持同一业务动作完整。** 将该动作涉及的多个页面、字段、按钮、接口及正常／异常步骤归并为一个功能点。

3. **不得按界面或技术元素拆分。** 页面、字段、按钮、单条校验规则、错误提示、页面跳转、接口字段和单个测试场景，均不能单独作为 Function Point。

4. **区分普通异常与独立业务能力。** 普通异常归入主功能；只有满足独立业务目标、角色、状态、资金或账务影响、运营流程等条件时，才独立拆分。

5. **区分内部作业与内部处理步骤。** 银行内部角色具有独立业务目标、处理状态或运营流程时，可以拆分；同一动作内部的系统校验或自动处理步骤不单独拆分。

6. **避免跨视角重复。** 同一业务能力即使同时涉及客户、渠道、风险、资金和监管等多个视角，也只保留一个功能点，并将相关要求合并到功能点描述中。

7. **保持粒度一致。** 同一报告中的功能点应具有可比较的抽象层级，不得将“办理贷款”与“展示贷款申请按钮”同时作为功能点。

8. **保持原文可追溯。** 每个功能点必须有明确原文依据，并能追溯到支持它的需求内容。

## 原文边界与 Open Items

1. 不得补充原文未明确说明的功能、业务规则、角色、状态、渠道、资金处理或监管要求。

2. 银行业务视角只能用于：
    - 识别原文明确涉及但尚未拆分的能力。
    - 检查已拆分功能点的描述是否完整。
    - 发现原文可能存在的遗漏、冲突或歧义。
    - 形成需要用户确认的 Open Items。

3. 对原文提及但含义、范围或边界不明确的内容，标注“待确认”，不得自行解释为确定规则。

4. 对根据银行业务视角发现、但原文未明确说明的内容，仅记录为 Open Item，不得直接建立 Function Point。

5. Open Items 应记录：
    - 编号。
    - 待确认事项。
    - 关联功能点或业务阶段。
    - 原文依据或原文缺口。
    - 对功能点边界或后续方案的影响。

## 输出要求

### Function Point 概览

功能点按客户旅程或产品业务生命周期排列；无法归入明确阶段的，按其在原文中的业务关系排列。

功能点概览使用以下字段：

| 编号 | 功能点 | 功能点描述 | 原文出处 |
|---|---|---|---|
| FP-001 | 创建贷款申请 | 客户创建并提交贷款申请；仅描述需求明确规定的行为、必要规则和业务结果。 | “需求原文摘录……” |

输出时遵守以下要求：

- “功能点描述”应说明必要的业务角色、业务动作、关键规则和业务结果，不描述页面或技术实现。
- “原文出处”应摘录支持该功能点的原始内容，可使用“……”省略非重点内容。
- 不得补充原文未明确说明的功能或业务规则。
- 对需求提及但含义或边界不明确的内容，标注“待确认”，并在 Open Items 中记录待确认事项及其影响。
- 使用连续编号，如 FP-001、FP-002，并在后续报告中保持编号和边界一致。
- 不增加业务视角、角色、业务对象或状态等额外表格字段；必要信息写入功能点描述。

### Open Items

如存在待确认事项，在 Function Point 概览之后单独列出；如无，则明确写“无”。

## 提交前检查

提交前逐项检查：

- 是否按业务能力而非页面、字段、接口或技术组件拆分？
- 是否按客户旅程或产品业务生命周期组织功能点？
- 每个功能点是否具有明确的业务动作和业务结果？
- 各功能点的粒度是否基本一致？
- 是否避免将 AC、单个校验规则或单个测试场景直接作为 Function Point？
- 是否将同一业务动作涉及的正常和异常步骤保持完整？
- 是否仅在角色、业务目标、处理状态或运营流程独立时拆分内部运营功能？
- 是否避免同一业务能力因不同渠道或不同业务视角而重复出现？
- 是否使用八个银行业务视角进行了识别和遗漏检查？
- 是否覆盖原文明确涉及的客户、产品、角色、渠道、状态、资金、风险、合规和监管要求？
- 是否将原文未明确说明的银行常见能力仅列为 Open Item，而非已确认功能点？
- 每个功能点是否都能追溯到原文？

## 用户确认

先提交 Function Point 概览及 Open Items，请用户确认或修正功能点及其边界；确认后再进入 Component 判定和方案讨论。

对标注“待确认”的内容，应在确认讨论中明确指出。未经用户确认，不得将其作为已确定的业务规则或后续方案依据。
