# Digital Solution Design（银行场景）

## 设计边界（先读这条）

- 范围内三个 area：Mobile（页面与内容）、AEM（网页版页面与内容）、API/Digital Service（能力需求：提供什么数据、什么行为、失败怎么办）
- 范围外（留给任务拆分环节）：endpoint 划分与命名、契约细节（URL/方法/字段名/版本）、component 选型
- 范围外（留给后端团队）：后端系统内部实现、DB、MQ——只列依赖，不做设计
- 边界外的事不做设计，但须追问其对前端的外露影响（如通知丢失的兜底感知、人工审核的中间状态），答案写入页面状态设计或依赖清单
- 链条定位：功能分析 → Grill 环节 → **产出方案** → TL 拆分任务（下游是任务拆分者，不是开发）

## 工作流程

1. **收集输入**：需求文档、UX/线框稿、渠道范围（Mobile/AEM）、现有后端能力清单、非功能需求
2. **功能分析**：拆功能点，按六视角逐一过（见下节）
3. **Grill 环节**：动笔前，逐个主动向用户追问关键问题（见 Grill 环节规则）
4. **按模板产出**：复制 assets/solution-design-template.md 填充
5. **自查**：过 references/checklist.md 兜底

### 增量更新模式（delta change）

输入含已有方案文档（旧版 solution-design.md）+ 变更需求时：
- 功能分析与 Grill 仅覆盖变更点，不重走全文
- 更新沿「页面 → 能力 → 依赖」追溯链逐层检查波及面，不只改用户指出的那一处
- 版本号 +1、状态重置为 Draft、填写模板文末「变更记录」

## 功能点拆解规则

- 以「客户/系统的一次完整动作」为单位拆（如：提交申请、查询进度），不以技术组件为单位
- 一个动作若有独立的依赖系统或独立的失败语义，拆成独立功能点（如：资格校验独立于提交申请）
- 拆完自检：每个功能点能独立填 §2.2 的一行（实现方 + 依赖系统 + 依赖类型），填不出来说明粒度不对

## 功能分析：银行六视角（每个功能点逐一过）

| 视角 | 必答问题 |
|---|---|
| 客户 | 旅程各步看到什么？失败时得到什么反馈？ |
| 渠道 | Mobile 与 AEM 行为是否一致？渠道限额差异？ |
| 风险合规 | 触发 KYC/AML/适当性/双录吗？哪步要强认证（短信/人脸/令牌）？哪些字段脱敏？哪些操作要留痕？——一票否决项，先于技术方案确认 |
| 账务状态 | 客户看到的状态与账务真实状态如何映射？（已受理 ≠ 已记账 ≠ 已清算）哪些结果 T+1 才确定？ |
| 运营外露 | 后端运营流程不做，但必须回答：有无人工审核（→"审核中"状态）？是否异步出结果（→"已受理"≠"成功"，结果如何触达）？驳回文案从哪个字段来？ |
| 系统集成 | 功能调用哪个后端服务（核心/ECIF/支付/信贷/风控…）？到此为止——后端服务内部实现不关心、不追问 |

产出：功能点清单，每个功能点标注 实现方 + 依赖系统 + 依赖类型（复用/改造/新增）+ 六视角实质发现。

## Grill 环节（动笔前必做）

对每个功能点/能力，主动向用户追问关键设计问题。题库见 references/grill-questions.md；业务特定问题现场生成。

交互规则：
- **一次只问一个问题**，得到回答后再问下一个；不一次性列问题清单给用户
- **由浅入深**：先问业务行为（客户在这个页面能做什么、拒绝后去哪），再问语义（重复提交意味着什么、数据能容忍多旧），最后问边界类（通知丢失客户怎么感知、中间状态如何外露）
- **问到服务名为止**：只需确认功能调用哪个后端服务、需要什么数据；后端服务的内部实现不追问、不假设
- 提问必须具体带场景（说"客户连点两次接受会怎样"，不说"要考虑幂等"）
- 用户答不上来的，标为 §10 Open Item 继续推进——不阻塞、不替用户假设
- **不设问题数量上限**：按风险排序逐个问，问到完全 clarify 为止

## 粒度标准

- **API / Digital Service**：精确到「能力」——提供什么数据、同步/异步、行为语义（时效/重复提交/送达兜底）、失败语义（阻断/降级）。不出现 endpoint；一个 endpoint 承载多个能力是下游的打包决策
- **Mobile**：精确到页面——改哪些页面、每页改什么内容、页面所需数据可追溯到能力清单
- **AEM（网页版）**：精确到页面；组件只写复用/新建意向，具体选型留给下游
- 验收：TL 拿任意一节能直接拆任务，不需要回来问"到底要给什么数据"

## 硬性原则

- 业务逻辑放 Service 侧，端上做薄（规则变更不发版；限额等参数可配置，不写死端上）
- 每个能力/字段标失败语义：阻断 or 降级
- 涉及资金的功能点：页面状态枚举与后端账务状态的映射必须显式写出
- 敏感字段（卡号/证件号/余额）脱敏规则写进能力的数据说明
- 每条后端依赖标 复用/改造/新增 + 状态
- 异常体验（超时/500/弱网）各端表现必须覆盖

## 输出

- Markdown 文档，命名：{功能名}-solution-design.md
- 架构图（§3）必须有；关键链路时序图（能力粒度，§6.3）必须有
